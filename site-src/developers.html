FOR DEVELOPERS & DATA CONTRIBUTORS

古墳データを、
安全に速く届ける設計。

古墳めぐりは、Haskellで検証・生成する静的サイトです。公開時にサーバーやデータベースを必要とせず、 ブラウザだけで地図・検索・詳細表示・クイズを動かします。

GitHub Pages静的ホスティング

01 / PRINCIPLES

設計方針

Static first

検索やクイズのためのAPIサーバーを置かず、生成済みファイルだけを配信します。運用箇所と障害点を減らします。

Reproducible data

外部APIを閲覧のたびに呼ばず、権利情報を含むJSONスナップショットをリポジトリで版管理します。

Rights by design

画像ごとに作者・ライセンス・元ページを保持します。再配布条件が不明なDBは複製せず、公式検索へ案内します。

Progressive loading

一覧は軽量プレビューを使い、大きい360度写真は利用者がビューアーを開始した時だけ読み込みます。

03 / HASKELL BUILD

Haskellは何を担当するか

実行ファイル kofun-build は、データを信頼して単にコピーするのではなく、 JSONを型へデコードして不整合を検出した後に公開物を生成します。

  1. 1
    Decode

    AesonでID、名称、WGS84座標、画像・パノラマフラグを型付きで読み込みます。必須フィールドの欠落や型違いはビルド失敗になります。

  2. 2
    Validate

    空ID・空名称、重複ID、緯度経度の範囲、パノラマと画像フラグの整合性を検証します。

  3. 3
    Render

    掲載数・画像数・360°件数をテンプレートへ埋め込み、トップと開発者ページを生成します。

  4. 4
    Package

    JSONをブラウザ用JavaScriptへ包み、CSS・JavaScript・画像・manifest・robots・sitemapをdocs/へ集約します。

data/kofun.json
  └─ Aeson decode → [Kofun]
       └─ validateRecords
            ├─ renderTemplate → docs/index.html
            ├─ renderTemplate → docs/developers.html
            ├─ JSON wrapper  → docs/assets/kofun-data.js
            └─ copy assets   → docs/assets/

Haskellを閲覧時のバックエンドとしては使いません。型検査と失敗の早期発見を公開前に集中させ、 配信後はCDNで扱いやすい静的ファイルだけにするためです。

04 / DATA MODEL

正規データモデル

現在のスナップショットは {{KOFUN_COUNT}} 基、画像付き {{IMAGE_COUNT}} 基、360°写真 {{PANORAMA_COUNT}} 基です。

フィールド役割例・注意点
id永続的な一意キーwikidata-Q... / kofun360-...
name, reading, aliases表示と全文検索別称も正規化検索の対象
lat, lngWGS84座標地図マーカーと近傍統合に使用
prefecture, location地域絞り込み所在地の粒度は取得元に依存
shape, length, period考古学的な基本属性不明値は空文字。推測で補完しない
sources, sourceUrl来歴統合レコードは複数出典を保持
image画像と権利情報作者、ライセンス、元ページ、altを保持
panoramaUrl360°原画像開始操作まで読み込まない

Kofun360との統合は、名称を簡易正規化して候補を絞り、座標が750m以内の最短レコードへ結合します。 自動統合規則を変更する場合は、同名古墳の誤結合が起きないか差分を確認してください。

05 / BROWSER RUNTIME

ブラウザ側の構成

State

検索語、都道府県、画像・360°、出典、地図／一覧、表示件数を単一の状態オブジェクトで管理します。

Search

NFKC・小文字化・空白や表記記号除去を行い、名称、読み、別称、所在地、形状、時期、説明を横断します。

Map

Leaflet 1.9.4とCanvasレンダラーを使い、OpenStreetMap帰属表示を常時表示します。

Details

ネイティブ<dialog>へ情報とライセンスを描画し、出典ページへ戻れるようにします。

Panorama

Pannellum 2.5.7を明示操作後に初期化し、大容量原画像の不要な転送を避けます。

Quiz

掲載データから問題と誤答候補を動的生成します。問題用の別データベースは持ちません。

フレームワークやバンドラーを置かないのは、データ図鑑として依存更新と配信サイズを抑えるためです。 レコード数が大幅に増えて描画が重くなった場合は、Web Worker、空間インデックス、データ分割を検討します。

06 / LOCAL WORKFLOW

ローカル開発

通常のサイト変更

cabal update
cabal build kofun-build
cabal run kofun-build
python3 -m http.server 8000 --directory docs

http://localhost:8000/で確認します。編集元はsite-src/で、docs/は生成物です。

オープンデータを更新

node scripts/sync-data.mjs
cabal run kofun-build
git diff -- data/kofun.json docs/

同期にはNode.js 20以降、ImageMagick、ネットワーク接続が必要です。 件数だけでなく、削除数、画像ライセンス、統合結果、異常な座標をレビューしてください。

07 / CI & DEPLOYMENT

GitHub Pagesへの配信

mainへのpush、または手動実行で次の順に処理します。

checkout→GHC / cabal→cache→build→generate→artifact→Pages

buildジョブはソースを読むだけです。deployジョブだけにpages: writeと OIDC用id-token: writeを与え、権限を最小化しています。

08 / LICENSE BOUNDARY

データを追加する前の確認

  • データセットの利用規約と、個別画像のライセンスを別々に確認する。
  • 作者名、ライセンス名・URL、元ページURLを失わない。
  • CC BY / CC BY-SAは必要な帰属を詳細画面に表示する。
  • 再配布許諾が確認できないデータは保存せず、公式サイトへのリンクにする。
  • 外部サービスのAPI、レート制限、タイル利用方針を守る。

プロジェクトコードは0BSDです。第三者データ・画像にはそれぞれの条件が適用されます。

09 / LIMITS & ROADMAP

現在の制約と拡張方針

  • 全国完全収録ではない自由利用条件を確認できた地点を優先。許諾済みデータは同じスキーマへ追加できます。
  • 共同編集データを含む位置や説明を学術的な確定情報として扱わず、公的機関・報告書への入口にします。
  • クライアント内検索数千〜数万件へ増える場合は、都道府県別チャンクと検索インデックスを生成時に作ります。
  • 自動統合は保守的名称と距離だけで確定できない候補は別レコードとして残し、手動対応表の導入を検討します。
